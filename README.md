# Bank API — автотесты

![API tests](https://github.com/AndrewShabailov/Swagger_api/actions/workflows/api-tests.yml/badge.svg)

Фреймворк для API-автотестов учебного банковского сервиса: пользователи, банковские счета, пополнения, переводы и кредиты. Тестовые данные генерируются фабриками на базе Faker по требованиям, тесты запускаются в GitHub Actions на каждый push против бэкенда, поднятого в Docker.

## Стек

- Python 3.14, pytest
- requests — HTTP-клиент
- Faker — генерация тестовых данных
- pytest-html — HTML-отчёт
- GitHub Actions + Docker — CI

## Что покрыто

Создание пользователя администратором (`POST /api/admin/create`):

- позитивные сценарии для ролей `ROLE_USER` и `ROLE_CREDIT_SECRET`;
- граничные значения длины username: 3, 4, 14, 15 символов;
- негативные кейсы username: короче 3 и длиннее 15 символов, спецсимволы, кириллица, пробел, пустая строка;
- негативные кейсы пароля: короче 8 символов, без заглавной, строчной, цифры или спецсимвола, кириллица, пустая строка;
- повторное создание пользователя с тем же username, включая проверку текста ошибки;
- запрос без токена авторизации.

В планах: банковские счета, deposit, transfer, история транзакций, кредиты.

## Тестовые данные

Ограничения из требований собраны в одном месте, в классе `Limits` в `factories.py`. Каждая фабрика отдаёт три вида данных:

- `valid()` — случайное значение, гарантированно проходящее валидацию;
- `boundary_valid()` и `boundary_invalid()` — граничные значения (min, min+1, max−1, max и min−1, max+1);
- `invalid_cases()` — негативные значения по классам эквивалентности.

Каждый прогон использует новые данные, а любое поле можно переопределить:

```python
user = UserFactory.build(Role.CREDIT_SECRET)          # валидный пользователь
weak = UserFactory.build(password="weak")             # негативный кейс
Deposit.boundary_invalid()                             # [999, 9001]
```

## Структура

```
.github/workflows/api-tests.yml     CI: поднимает бэкенд в Docker и запускает тесты
src/main/api/
├── clients/                         слой работы с API
│   ├── endpoints.py                 все пути API в одном месте
│   ├── base_client.py               сессия requests, базовый URL, токен, таймаут
│   ├── auth_client.py               логин
│   └── admin_client.py              создание и удаление пользователей
├── models/
│   └── request_models.py            модели тел запросов (dataclass)
├── data/
│   ├── config.py                    BASE_URL и креды админа (из переменных окружения)
│   └── factories.py                 фабрики тестовых данных на Faker
├── conftest.py                      фикстуры: клиенты, создание пользователей с автоудалением
└── tests/
    └── admin/
        └── create_user_test.py      тесты создания пользователя
pytest.ini                           настройки pytest
requirements.txt                     зависимости с закреплёнными версиями
```

Тесты не работают с `requests` напрямую: запросы идут через клиенты, а пути хранятся в `Endpoints`. Если меняется эндпоинт, правится одна строка. Пользователи, созданные в тесте, удаляются фикстурой `create_user` после теста, в том числе при его падении.

## Известные баги

Тесты на найденные дефекты помечены `xfail(strict=True)`: пока баг есть, тест отображается как XFAIL и не роняет прогон. Когда баг исправят, тест станет XPASS и упадёт, напоминая снять пометку.

- На повторное создание пользователя с существующим username сервер возвращает 409 с сообщением про лимит банковских счетов вместо ошибки о занятом имени.

## Локальный запуск

1. Поднять бэкенд:

   ```
   docker run -d -p 4111:4111 andrewshabailov/bank_api:latest
   ```

2. Установить зависимости и запустить тесты:

   ```
   python -m venv .venv
   .venv\Scripts\activate          # Windows
   pip install -r requirements.txt
   pytest --html=reports/report.html --self-contained-html
   ```

Адрес API и креды админа берутся из переменных окружения `BASE_URL`, `ADMIN_USERNAME` и `ADMIN_PASSWORD`. Если они не заданы, используются значения по умолчанию из `config.py`.

## CI

Workflow запускается на push в `master`, на pull request и вручную (Run workflow во вкладке Actions):

1. поднимает бэкенд как service-контейнер;
2. ждёт, пока API начнёт отвечать;
3. запускает тесты;
4. сохраняет HTML-отчёт и JUnit XML как артефакт `test-report`, в том числе при падении тестов.

Креды админа хранятся в GitHub Secrets.
